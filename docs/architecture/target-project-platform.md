# Briareus — продуктовая модель и MVP

## Пользователи, команды и проекты

Rauthy владеет пользователями, учётными данными, MFA, identity-токенами,
группами и ролями. Control Plane хранит предметные связи пользователей,
команд и проектов с проверенными issuer/subject, не создавая вторую систему
паролей или независимых пользовательских ролей.

Team объединяет людей для совместной работы. Project принадлежит человеку
либо Team; перенос ownership и удаление владельца не должны терять проекты,
файлы и ресурсы. В MVP проверяется текущий доступ пользователя к проекту/
группе: участник может выполнять все действия внутри этого проекта.
Более детальные человеческие права на отдельные действия — следующий этап.

Один логический Project имеет один UUID в Control Plane и на всех его Node.
Размещение определяется парой Node UUID + Project UUID. На каждой Node
отдельные workspace, сессии, доступы, ресурсы и исполнение. Совпадение UUID
не создаёт общей ФС, автоматической синхронизации или переноса полномочий.

## Вход и начальный администратор

Все экраны входа, MFA и восстановления находятся в Control Plane UI.
Путь: UI → Control Plane backend → приватный Rauthy. Backend ведёт приватный
поддерживаемый протокол провайдера и его сессии/challenges; Rauthy проверяет
данные и выпускает токен, возвращаемый обратно. Отдельного инфраструктурного
сервиса Authorization нет. UI вызывает backend RPC по WSS с бинарным
Protobuf. Внутренние сервисы используют native gRPC или WSS-адаптер тех же
типизированных RPC-контрактов; семантика не зависит от транспорта. WSS не
является native gRPC/HTTP2. Стандартный MCP и нативные протоколы внешних
провайдеров сохраняются; отдельный REST CRUD или GraphQL не закладывается.

Rauthy создаёт начального администратора при инициализации пустого провайдера.
Вход выполняется через нашу панель. Нет регистрационной ссылки в логах,
назначения прав первому посетителю или повторного bootstrap из-за отсутствия
локальной пользовательской проекции. Пароли и ключи Rauthy не копируются Node.

## Node и MCP-модули

Node автономна: Gateway, Node Access/Cedar, несколько локальных размещений
проектов, сессии, модульные контейнеры, файлы и служебное состояние.
Пользователей, групп, команд и Rauthy внутри Node нет. Она запускается,
управляет своими проектами/модулями и работает без внешней панели и её
сервисов. Панель добавляет управление Node, пользователей, группы и совместную
работу; её наличие не является условием локального исполнения.

Каждый MCP-модуль имеет один каталог исходников и собственный Compose;
Node разворачивают разные наборы из этого каталога. Наличие исходников
не означает, что модуль установлен, запущен и доступен на конкретной Node.

Files, Browser, Terminal и остальные модули подключаются отдельными MCP-
подключениями через Node Gateway. Инструменты не объединяются в одну MCP.
Доступ может идти прямо к Node либо через Gateway Control Plane с сохранением
выбора Node/модуля. Project выбирается доверенным контекстом сессии.

## Управление и события

Панель — единая точка человеческого управления; backend хранит пользователей,
связи команд/групп/проектов, область человеческого управления и учёт размещений.
Локальный проект создаётся и хранится самой целевой Node по RPC-команде.
Один Project может присутствовать на одной Node и отсутствовать на другой.
Node не хранит людей, команды, группы, владельцев и их роли.

Все сессионные запросы, grants, решения и проверки формируются и хранятся
в Node. Backend получает события и хранит проекцию для интерфейса, а не
второй источник операционных разрешений. Node-wide представление группирует
доступные данные по Node, проектам и сессиям. Project-wide представление
показывает один логический Project на его доступных Node независимо от
группировки по Node. Права человека проверяет инфраструктура; выбор Node
не открывает человеку чужие проекты, а членство в Project не даёт управления
всей Node. Эти человеческие области не передаются в Node как IAM-модель.

Кроме событий, управляющий RPC обязан возвращать все актуальные активные
запросы с ограниченной пагинацией, фильтрами Node/Project/session/status и
точным чтением состояния/ревизии. Ручное обновление и reconnect сверяют
проекцию backend с Node. Offline и устаревшее наблюдение отображаются явно;
отсутствие события не означает согласования, удаления или отсутствия запроса.

При discovery Node сама устанавливает канал наверх. Без discovery панель
подключается к настроенному Gateway независимой Node. Направление
установления соединения не меняет владельца состояния или полномочий:
Node посылает события по этому же каналу, backend — управляющие команды.

Полный управляющий API находится за входящим в Node Gateway. Поддерживаются
native gRPC и WSS с бинарным Protobuf, едиными контрактами, сценариями,
валидацией и правилами доступа. Постоянный двусторонний канал передаёт
команды, результаты и события; соединение инициирует Control Plane или Node.

В доверенной внутренней сети MVP дополнительный пользовательский/OAuth
или caller-login слой управления не требуется. Полный управляющий интерфейс
отделён от недоверенных MCP-вызовов и ограниченных сессионных команд.

Node сообщает событием о pending-запросе. Backend уведомляет пользователя;
решение возвращается по тому же логическому каналу. Node не знает людей и
их роли. Повторное соединение/команда не дублирует выданный доступ или эффект.

Явный standalone-режим может работать без MCP OAuth, сохраняя сессии/Cedar.
Отказ аутентификации подключённого режима не включает standalone автоматически.

## Рубильник согласования сессий

Node имеет явные режимы enforced и auto-approved, независимо от подключения
панели или MCP OAuth. В auto-approved автоматически подтверждаются все
валидные сессии и все их действия внутри своего проекта: ждать пользователя
или согласующего и получать отдельные операционные grants не требуется.
Сессия сохраняется как источник действий; новое создание возвращает готовую
сессию, решение фиксируется как автоматическое.

Изоляция проектов обязательна в обоих режимах. Сохраняются привязка и жизненный
цикл сессии, валидация команд/ресурсов и аудит. Рубильник не открывает соседние
проекты, не назначает согласующих и не даёт MCP-клиенту полного управления.
Меняет режим только доверенное управление. Возврат к enforced требует явных
grants для новых действий; автоматические решения не превращаются в вечные
доступы. Пользовательский вход/права инфраструктуры — отдельный слой.
Подробности: [режимы сессионного доступа](session-access-modes.md).

## Сессия и доступы (enforced)

AgentSession — единица операционных доступов, а не достоверная постоянная
идентичность агента. Один клиент может открыть несколько независимых сессий.
MVP-метаданные: заявленное имя/тип агента, цель/задача и необязательный чат.
Они помогают рассмотреть запрос, но не удостоверяют личность или ownership.

Сессия принадлежит Node/Project и может использовать несколько MCP-точек
этой Node в пределах выданных доступов. Для защищённых действий нужна сессия;
создание сессии не требует прежней сессии и само не выдаёт защищённых операций.
Новая сессия не наследует доступы по имени агента, чату или прошлой сессии.

Запрос доступа поступает в Node Access/Cedar, не Rauthy. Пользователь проекта
может одобрить/отклонить его через Control Plane. Другая согласующая сессия
делает это через ограниченный сессионный интерфейс в своей Node/scope.

Только человек/оператор через полное управление назначает согласующую
сессию. Она выдаёт операционные доступы, но не назначает других согласующих,
не согласует собственный запрос, не управляет другой Node или Control Plane.
Разные session_uuid не доказывают, что за ними разные реальные агенты.

## Сроки явных доступов и сессии

Каждый доступ имеет свой scope и конечный срок либо явно бессрочный режим.
Активность/keepalive не продлевает доступ на пять минут. Изменение срока —
отдельное подтверждённое решение уполномоченного согласующего/управления.

В enforced истечение прекращает только этот доступ: сессия, остальные разрешения и
возможность нового запроса сохраняются. Новая операция проверяется при допуске.
Уже допущенная и запущенная операция завершается после истечения без
автоматического прерывания. Явные отзыв/отмена/остановка — отдельные команды.

Отдельно каждое принятое действие обновляет idle/last-activity в локальном
Valkey/KV. Это не меняет grants и не возрождает остановленную сессию.
Автоматическая остановка по бездействию и уборка — после MVP. Явная остановка
требует соответствующего полномочия; согласование не даёт его автоматически.
Общие файлы проекта не удаляются только потому, что сессия ими пользовалась.

## Файлы, состояние и общие ресурсы

Workspace один на Project/Node, общий для его Files/Terminal/Browser/MCP.
Сессии не получают доступ к соседним workspace, home, профилям и секретам.
Нужна реальная filesystem/runtime изоляция, а не только имена каталогов.

Межпроектная передача файла/директории выполняется внешним интерфейсом с
target_node_uuid и target_project_uuid, даже внутри одной Node. Проверяются
обе стороны. При перемещении сначала подтверждается запись/целостность,
затем отдельно разрешается удаление исходника. Доступы с данными не едут.

Node владеет файлами, сессиями/grants и журналом через SQLite/PostgreSQL
адаптеры. Необязательные KV/вычислительные БД тоже её собственные.
Центральный Resources не является runtime-БД Node.

Team-ресурсы явно привязываются и доставляются в локальную БД Node.
Рабочая операция получает секрет локально. Control Plane инициирует обновления
и периодическую/повторную сверку версий; Node не опрашивает каталог секретов.
Без связи сохраняется последнее применённое состояние, с учётом действительности
токена у провайдера. Изменение источника действует после доставки.

## Организация и проверка

На Node есть отдельная общая постоянная папка: все локальные проекты могут
читать и писать её содержимое без ограничений по проектам/записям и без
индивидуальных grants. Node наблюдает её состояние и фиксирует действия
сессий для аудита без содержимого файлов/секретов. Это сознательно общие
данные, не путь в приватные каталоги другого проекта. Приватные файлы,
home/профили/credentials и БД анализаторов туда автоматически не копируются.
Между Node общая папка автоматически не синхронизируется.

Системные toolchain — другой механизм: панель задаёт набор/версии,
Node автоматически устанавливает их через image/Compose потребляющих
модулей и сообщает фактическую доступность. Python, Node.js, uv и другие
выбранные инструменты доступны как системные программы; установка доступна
агентам только для чтения. Локальные зависимости/окружения проекта остаются
изменяемыми. Добавление/удаление инструментов — управление Node; изменение
общей папки не меняет системную установку. Обновляются только контейнеры,
которые действительно потребляют изменившийся набор, с сохранением данных.

Runtime сгруппирован в infrastructure/ и hands/; узкие shared-пакеты имеют
явных потребителей. Модуль владеет сборкой/Compose/зависимостями, а Watch
включает только его и потребляемые shared-пути.

Сначала завершаются исходники всех направлений, затем по отдельному
разрешению начинается тестовая фаза. Связные блоки публикуются самостоятельно
после локального запуска, линтеров/типов, тестов и hooks по исходящей ревизии,
без мелких push и повторного одинакового CI. Существующие данные и разрешённые
границы Dev сохраняются; документация не доказывает готовность runtime.
