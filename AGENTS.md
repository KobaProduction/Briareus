# Briareus — Infrastructure / Hands / focused Shared packages

## Mandatory engineering rules

Before any implementation/refactoring, every agent MUST read [Briareus Clean Architecture / DDD adoption](docs/architecture/clean-architecture-ddd-briareus.md), the linked [AI Agent Workflow reference](docs/architecture/ai-agent-workflow/clean-architecture-ddd.md), and [local quality policy](scripts/quality/README.md). These apply to ALL first-party services, MCP Hands, shared libraries and UI; no per-service opt-in.

**Refactoring tool priority:** Prefer working semantic inspection and refactoring tools built into the current environment, editor, IDE or Codex. Use Serena MCP only as a fallback when the required native tools are absent, unavailable or not working. Check the capabilities actually exposed in the current session; do not assume a native refactoring tool exists. Do not start or keep Serena/LSP processes running when native tools cover the work. When the fallback is needed, use Serena with the appropriate Python/TypeScript/Vue LSPs and obey the singleton rule below.

**Serena singleton:** At most ONE Serena MCP server instance is allowed for the entire Briareus project, across all chats and agents. Reuse the existing project server and its Python/TypeScript/Vue LSPs; do not start a server per chat, agent, service, or task. Before starting Serena, verify that no project instance already exists. If a client cannot reuse the existing connection, report that limitation instead of spawning a duplicate. For STDIO clients that cannot share a connection, only the designated owner invokes Serena; other agents request semantic inspection from that owner instead of initializing their own connection. Report client-side automatic duplicate startup rather than repeatedly reconnecting or starting another server. Reconnect to or restart the single instance only when it is unavailable, coordinating with its current owner to avoid disrupting active work.

Domain owns invariants and typed entities/value objects; application owns use cases and ports; infrastructure owns storage/provider/process implementations; presentation adapts existing HTTP/WebSocket/gRPC/MCP contracts. Dependencies point inward. Frontend retains FSD, entity models and shared UI with no cross-slice implementation imports. No framework/ORM/network/process dependencies inside domain, no service-to-service persistence imports, no business orchestration inside routers/components.

Owner quality contract: cognitive complexity <=15 in production and <=30 in tests; no Any or untyped Python functions; no ordinary dictionary result contracts (use dataclass/NamedTuple/typed models). Do not weaken gates, add blanket ignores or preserve a duplicate implementation to make checks pass. Architectural extraction must preserve authority, runtime isolation, event ordering and idempotency; no speculative schema reset, protocol change or new pattern without a real invariant. Publication follows the local-validation and coherent-batch contract below, not a blanket push prohibition.

Parallel agents own disjoint files/modules, coordinate shared contracts through the root agent and direct peer messages, and never revert peer edits. No new local task/backlog/report Markdown; report progress in chat and keep machine diagnostics under ignored artifacts/. Current owner scope excludes CI changes, shell/Docker/Compose lint expansion, third-party code changes and deferred feature expansion. Complete foundation/source work across ALL owners before the separate later test phase. Scoped Biome/Ruff/mypy/type diagnostics are allowed as needed during source work. Remove incompatible legacy implementations and obsolete compatibility paths after resolving actual consumers; retain useful mechanisms with their correct owner. Delete tests exclusive to removed/incompatible legacy contracts, not tests exposing current defects or preserving applicable invariants. Do not run, write or adapt new/retained tests or fixtures during this source phase; diagnostic tests and per-block acceptance are not exceptions. No broad frontend refactor belongs to this cleanup. Test/fixture adaptation and final aggregate acceptance begin only in the separately authorized next phase after all owners finish their source work. Do not run tests/builds after every function or extraction. Mandatory quality hooks remain enabled.

**IDENTITY/AUTH DESIGN:** docs/architecture/identity-and-session-access.md (Rauthy + Cedar).
**AUTHENTICATION:** `Control Plane UI → Control Plane backend → private Rauthy`. Backend owns the pinned private provider protocol, sessions/challenges/CSRF/PoW/MFA/OIDC state and protected administration credentials. Rauthy exclusively stores/verifies human credentials and issues/revokes identity tokens. UI owns all login/MFA/recovery screens and uses backend RPC over WSS. Provider state/keys never reach UI or Node; passwords/MFA secrets are never persisted/logged by Briareus. No separate infrastructure Authorization service or second identity signer/password verifier. Missing required provider evidence fails closed.
**RUNTIME BOUNDARIES:** Infrastructure owns users/Teams, Rauthy-backed identity and human rights, central Projects/Node attachment and the Panel. Each Node owns multiple isolated local Projects, Node Access session grants/Cedar, Gateway, its MCP module set and execution state. It has no users/groups/Teams/Rauthy requirement. Connected management commands carry trusted human/Project authority into Node Access; final session-effect decisions are local. Each Node can start, manage local Projects/modules and execute work without the Panel or external infrastructure services. Explicit standalone mode may omit MCP OAuth while retaining the Node session model. No authentication-outage fallback or implicit management authority. Preserve existing state and approved deployment scope.
**INITIAL ADMINISTRATOR:** Rauthy creates its initial administrator during empty-provider initialization; sign-in uses UI → backend → private Rauthy. No registration link in logs or first-visitor role assignment. Preserve provider state; no log password scraping or reinitialization because a local projection is absent.
**ACCESS OWNERSHIP:** Infrastructure/Rauthy owns human identity/groups/rights; backend checks human Node-wide management scope and Project-wide membership before queries/commands. An MVP Project member may manage/approve within that Project, not the entire Node or unrelated Projects. Node Access exclusively owns local sessions, requests, grants, Cedar and audit. Backend stores event projections for Node-wide/Project-wide views and refreshes through paginated active-request RPC and revision/cursor reconciliation; projections grant nothing. Human-appointed approver sessions act only in their Node/scope, never appoint approvers, self-approve the same requesting session or gain upstream rights. Metadata is untrusted.
**SESSION-ACCESS MODES:** Node supports explicit enforced and auto-approved modes independently of Panel attachment and MCP OAuth. Auto-approved automatically confirms every valid session and all its in-Project actions without manual review or individual operational grants. Node Access returns that decision through the same Gateway/module contract; no per-module bypass implementation. Project isolation is unconditional: preserve active session/Node/Project binding, filesystem/process boundaries, valid commands/resources and audit. The switch never grants approver authority, full management, another Project/Node or human infrastructure rights. Only trusted full management changes mode. On return to enforced mode new work needs explicit valid grants; automatic decisions do not become permanent grants. Record mode changes/automatic admission without fictitious human decisions. Mode does not change on outage. See docs/architecture/session-access-modes.md.
**AGENT SESSION MODEL:** Delegated operational grants and human-issued approval authority belong to a specific AgentSession UUID, never a persistent inferred agent/chat identity. One MCP caller may create multiple independent sessions; no grant/approver authority transfers automatically to a new session. MVP metadata (claimed agent name/type, purpose/task, optional chat reference) is untrusted review context. Require a session for protected effects. In enforced mode creation itself grants none; auto-approved mode returns a ready session and automatically approves in-Project actions. Separate hard approved access deadlines from sliding session idle/liveness. Accepted active-session activity refreshes only idle state in Valkey; it never extends a five-minute access grant, broadens scope or revives stopped/revoked state. In enforced mode each grant has its own scope/deadline; expiry disables only that grant, preserves the session and other valid grants, and allows a new access request. Grant expiry is not session stop or blanket revocation. In enforced mode check the relevant grant when admitting new work; already admitted/started operations may finish after expiry. Do not terminate them solely because the deadline elapsed. In enforced mode subsequent operations require a current grant; explicit cancellation/stop is separate. Explicit deadline changes require a separate authorized audited decision. Durable session grants/revocation stay in the owning Node persistence port, with explicit SQLite or PostgreSQL adapter; never central Resources storage. Access may be explicitly non-expiring and always revocable. Automatic inactivity shutdown/resource garbage collection is post-MVP; explicit stop requires a user or specifically stop-authorized session. OAuth/peer-proof expiry is independent. Prevent approval of the same requesting session; do not claim different sessions prove distinct real-world agents.
**MCP MODULE PLACEMENT:** Each MCP module has one catalog directory under Hands, optionally grouped, and owns its Compose/dependencies. Node instances independently select/enable/disable module container sets. Known, installed, running and callable states are distinct; catalog presence alone does not make a module executable.

**FIRST-PARTY RPC:** UI/backend/internal management uses typed gRPC service/Protobuf contracts with native gRPC and WSS binary RPC adapters. Browser uses WSS; internal endpoints select a configured supported transport, preserving identical use cases/errors/authority/idempotency. WSS is not native HTTP/2 gRPC. No parallel REST/JSON or selected GraphQL control API. Standard external MCP and provider protocols remain supported as specified.

**NODE CONTROL CHANNEL:** Node always includes Gateway. First iteration requires both native gRPC and WSS with binary Protobuf, one versioned command/result/event schema and shared Node application use cases. Both are persistent bidirectional transports; native gRPC uses HTTP/2, WSS is a separate adapter. Share validation, unconditional Project isolation and selected session-access mode enforcement, results/errors and correlation/idempotency across reconnects/transport changes; adapters own framing/connections only. No REST/JSON control API or independent per-transport policy. Support Core-initiated and Node-initiated connectivity. Trusted private MVP management needs no separate OAuth/user/peer-login layer; ordinary MCP workloads/public anonymous callers cannot use full management. Infrastructure checks human Project membership; Node knows local Projects/sessions. Pending events and human decisions use the same logical channel. Approver sessions are Node-local.

**NODE STORAGE AND FILE TRANSFER:** Each Node owns persistent files/workspaces, local Project/session/grant state and execution journal in both standalone and connected modes. Use application persistence ports with SQLite/PostgreSQL adapters; optional Valkey/KV/scratch stores are Node-owned too. No dependency on central runtime storage, global filesystem or automatic backend fallback. Provide explicit upload/download and cross-Node transfer ports through both binary control transports. Source/destination Node/Project checks are independent; files never carry session/approval authority. A move confirms destination write/integrity before separately authorized source deletion. Preserve existing data; documentation does not authorize migration/reset.

**PROJECT WORKSPACE ISOLATION:** Each Node-local Project owns one persistent private filesystem shared by its Files/Terminal/Browser modules. Working directories, repositories, worktrees/builds/toolchains are Project subdirectories, not independent Projects. Enforced mode requires applicable grants; auto-approved admits valid in-Project actions. No traversal/symlink/profile/home/credential access to another Project. Explicit Node-wide common storage is a separate deliberately shared read/write namespace, available to all local Projects without per-entry/session restrictions, with observation/audit; no automatic exposure of private Project data or secrets. Private cross-Project transfer uses explicit source/target Node/Project checks. Native analysis stores remain module-owned durable private data. See docs/architecture/node-storage-and-transfer.md.

**NODE COMMON FILES / SYSTEM TOOLS:** Node exposes separate persistent common storage readable/writable by all local Projects without per-entry or individual-grant restrictions, with session attribution, observation/audit and no automatic publication of private Project or module data. It is not cross-Node replication or a private Project path. System toolchains are separate: panel configures tools/versions, Node installs them through consuming image/Compose defaults; agents use system installations read-only and keep local environments writable. See docs/architecture/node-storage-and-transfer.md.

**RESOURCES AND SECRET SOURCES:** Node owns local Project resources and durable secret values, including values delivered from Team-shared/external sources. MCP operations resolve credentials locally with no per-action catalog fetch or Node secret-polling loop. Control Plane initiates initial delivery, source-change updates and periodic/reconnect version reconciliation through the existing gRPC/WSS channel. Node atomically applies scoped/versioned updates, acknowledges without values and rejects stale/duplicate effects. Disconnected Node retains its last applied state; remote changes apply after delivery, while provider credential validity remains independent. Shared source/secret versions never grant session access. Metadata/logs expose no values. See docs/architecture/resources-and-secret-sources.md.
**PROJECT IDENTITY:** One logical Project has the same Project UUID in Control Plane and every attached Node, with no separate local-ID translation. Node UUID + Project UUID selects local workspace, sessions/grants, resource bindings and execution state. Equal Project UUIDs never imply shared files, replicated state, grant inheritance or cross-Node approver authority; UUID/name selectors are not permission.

**MCP ENDPOINTS:** Clients connect separately to Files/Browser/Terminal/other module endpoints through Node Gateway; do not aggregate all tools into one MCP endpoint. Direct and panel-proxied ingress preserve Node/module selection. Each module retains its own MCP catalog and configured OAuth resource/audience. Route/readiness reflects the actual module set on that Node, not a fixed global set. AgentSession is Node/Project-scoped and independent of a connection; it may use multiple same-Node endpoints within its Project and the selected session-access mode. gRPC/WSS management is a separate interface.

## Owners
Backend: Control Plane backend private Rauthy integration, human identity/management scope, RPC coordination and event projections; Platform/Resources owner scenarios. No central Node session/grant authority. Coordinate typed Node contracts with Runtime.
Runtime: Hands Node controller, isolated local Projects, Node Access sessions/grants/Cedar, Node Gateway and Compose-based MCP modules. Direct and panel-proxied ingress use the same Node contracts. No user/group/team or Rauthy subsystem inside Node.
Frontend: infrastructure Control Plane UI owns native sign-in/MFA/recovery screens, management and session-request review; it communicates through Control Plane API.
Deployment: infrastructure Rauthy/PostgreSQL/Valkey, approved runtime provisioning and provider contracts. Each module preserves its independent source/build/Compose lifecycle.

## Autonomous release
**BATCHED DEVELOPMENT PUBLICATION:** Agents may commit/push/publish and deploy their owned changes within the assigned task and approved Development scope without approval for every push. Work primarily locally and accumulate a coherent reviewable block; do not commit/push each small action or repeatedly trigger CI. Before publication, run the affected local components and verify behavior, linters/types, appropriate tests and mandatory hooks against the actual staged/outgoing revision and its affected dependency consumers. Never include unverified peer changes or bypass gates. Preserve the aggregate source-first/test-phase rule: finish all source owners, obtain separate test-phase authorization, then complete validation before publishing that batch. Successful checks are not rerun without changed inputs or unresolved concerns; one final full aggregate check applies at the completed test-phase boundary. `main` remains the Development branch where actual repository protection permits ordinary push; otherwise follow the required PR/check path. No force push, Production change, unrelated resources, speculative reset or gate weakening is authorized. Preserve approved app UUIDs, data and current rollout/rollback boundaries.
